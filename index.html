An end-to-end coding assessment system built to make online evaluations harder to cheat. Combining isolated code execution, plagiarism detection, anti-cheating controls, and automated candidate ranking.

Walkthrough

01

Overview

Unbiass grew out of LC Police, a tool I originally built to detect suspicious submissions in LeetCode contests. As AI-assisted solving and external cheating tools became easier to use, detecting cheaters after a contest started to feel like only half the problem.

I expanded the idea into a company-facing assessment platform that handled coding questions, MCQs, code execution, plagiarism analysis, anti-cheating signals, and candidate ranking as one pipeline.

2.5K+ daily active users
100K+ interactions
30K+ LeetCode submissions analyzed
02

Problem

Online coding assessments increasingly operate in an environment where candidates can use AI coding assistants, copied solutions, external answer-sharing tools, or even OS-level overlays that are invisible to normal browser monitoring.

I wanted the evaluation pipeline itself to account for this instead of treating cheating detection as a separate moderation step.

03

What I built

Unbiass covered the assessment lifecycle from candidate entry to the final shortlist.

  • Coding and MCQ-based assessments
  • Candidate-specific contest access
  • Code execution for C++, Java, Python, and JavaScript
  • Pretest and full-test execution
  • Submission state tracking
  • Cross-candidate plagiarism detection
  • Browser-level anti-cheating signals
  • Client/admin contest configuration
  • Automated candidate scoring and ranking

I designed and implemented roughly 95% of the system myself, including product architecture, frontend, backend, execution infrastructure, plagiarism pipeline, contest logic, and most deployment work.

04

Architecture

The frontend communicated with a Go/Gin backend responsible for contest state, submissions, candidate data, MCQs, and client workflows. PostgreSQL stored persistent application data, while Redis tracked temporary submission/result state.

Coding submissions were processed asynchronously by concurrent workers and executed inside isolated Docker environments. After the contest, eligible submissions passed through the plagiarism and ranking pipelines before the final candidate list was generated.

flowchart TD A[Candidate] --> B[React Frontend] B --> C[Go / Gin API] C --> D[(PostgreSQL)] C --> E[(Redis)] C --> F[Submission Queue] F --> G[Concurrent Workers] G --> H[Docker Execution] H --> H1[C++] H --> H2[Java] H --> H3[Python] H --> H4[JavaScript] H --> I[Pretest Results] I --> J[Plagiarism Pipeline] J --> K[Candidate Scoring] K --> L[Ranked Candidates]
05

Code execution

Candidate code is untrusted input, so execution was isolated inside Docker environments rather than running directly on the application host. Separate execution environments were maintained for C++, Java, Python, and JavaScript.

A submission was first persisted and acknowledged by the backend. It then entered the execution pipeline, where a worker picked it up, loaded the required pretests, selected the correct language environment, executed the code, and updated the submission state.

The frontend polled for that state and surfaced outcomes such as accepted, wrong answer, time-limit exceeded, or memory-limit exceeded.

Running every submission against 50–100 full test cases immediately was too expensive for the available infrastructure, so I borrowed a Codeforces-style idea: run a much smaller pretest suite first and defer the expensive full evaluation until later in the pipeline.

06

Plagiarism detection

Comparing raw source code was not enough because copied solutions can be modified through comments, templates, formatting, renamed variables, and other superficial changes.

The pipeline therefore progressively reduced the code before comparing submissions.

  • Remove comments, templates, and redundant code
  • Extract the logic-relevant portion of the submission
  • Convert it into an AST / structural representation
  • Compare submissions against one another
  • Generate a similarity / plagiarism score
  • Use LLM inference as another signal in the pipeline
  • Surface suspicious cases for human validation where necessary

Models used across the inference experiments included Llama 9B, Gemma 7B, and Mistral 3B through providers such as Groq and DeepInfra.

LC Police was tested against more than 30,000 LeetCode submissions. Rather than treating an AI-generated score as unquestionable truth, suspicious matches could be inspected by humans before making a final judgement.

07

Candidate ranking

The final ranking was not based only on how many coding questions a candidate appeared to solve.

Coding correctness, MCQ performance, and plagiarism signals were combined into the final candidate score. A candidate with fully correct answers and no plagiarism received the strongest score; incorrect answers and plagiarism progressively reduced it.

flowchart TD A[Coding Correctness] --> D[Candidate Score] B[MCQ Performance] --> D C[Plagiarism Penalty] --> D D --> E[Score Candidates] E --> F[Sort by Final Score] F --> G[Ranked Candidate Shortlist]
08

Anti-cheating

Browser monitoring could detect some candidate behaviour, but a harder problem appeared with tools such as Interview Coder that could render assistance at the operating-system layer without appearing normally in screen sharing or browser-level monitoring.

I built a C# overlay-detection prototype and explored connecting native detection with the assessment workflow. The experiment exposed a fundamental boundary: a browser application cannot reliably inspect everything happening at the OS level.

A complete solution would have required moving the assessment into a native application with deeper system permissions. That version was not completed before the project was discontinued.

09

Results

2.5K+ DAU for 2–3 months
100K+ interactions
30K+ submissions analyzed
2 early clients

LC Police also reached the top search result for its target query and generated enough interest for the project to evolve from a public cheating-detection tool into a company-focused assessment product.

10

What broke

The biggest mistake was building too much infrastructure before fully validating the product.

I built the compiler, execution environments, plagiarism pipeline, frontend, backend, monitoring experiments, deployment setup, and client tooling largely myself. That taught me a lot technically, but it also meant product validation moved much slower than it should have.

Multi-service deployment also became a weak point. I used Docker Compose, Nginx, custom deployment scripts, and Utho Cloud, but a production contest exposed how fragile the service communication and operational setup still was.

The native overlay-detection problem was another boundary I could not solve within the project's constraints.

11

What I'd change

  • Use third-party compiler infrastructure for the MVP instead of building the execution stack immediately.
  • Validate company demand before investing heavily in custom infrastructure.
  • Build with 2–3 strong engineers instead of trying to own frontend, backend, infra, AI, security, and product alone.
  • Narrow the first product to assessment and candidate ranking rather than trying to become an entire hiring platform.
  • Design assessments that are inherently harder to game instead of relying only on increasingly aggressive monitoring.

Built along the way, SlimUUID

While thinking about the amount of identifier data stored and indexed across the system, I went down a separate systems rabbit hole: could I make UUIDs substantially smaller while keeping them practical for application use?

The result was SlimUUID, An 18-character identifier format designed to reduce storage and indexing overhead compared with conventional textual UUIDs. I eventually separated it from Unbiass and open-sourced it as its own project.

00

Context

Nugget is Zomato's AI-powered customer-support platform, including voice agents used for inbound and outbound calling campaigns. I worked on the backend team, primarily around the systems that configure how those voice agents behave and the infrastructure supporting production customer workflows.

My work covered voice configuration across speech-to-text and text-to-speech providers, call reliability, knowledge-base response latency, and the quality-control ticketing infrastructure used by clients.

01

Voice configuration — Avatar

A production voice agent is more than a voice selection. Each call depends on a collection of settings across speech recognition, speech generation, pronunciation, compliance, and audio behaviour.

I worked on a major part of the newer voice-settings system, internally represented as an Avatar. The goal was to bring these previously default-driven settings into a single configurable voice configuration.

  • STT provider and model
  • TTS provider, model, and voice
  • Voice volume
  • Background noise configuration
  • Compliance messages
  • Client-specific pronunciation / enhancer dictionaries
  • Custom voices

I worked across the backend rollout as the system moved from pre-saved, non-editable defaults toward client-level customization across providers including Sarvam, ElevenLabs, Cartesia, and Groq.

02

Making custom voices self-serve

Custom voices created an operational problem. When a client needed a provider-specific voice, engineers had to manually validate the voice, add it to the development environment, test it, and then configure it in production.

The shared voice catalogue was also becoming increasingly noisy. I proposed separating the catalogue into a small set of tested, client-agnostic voices and a second set of client-specific voices. Standard voices remained shared, while custom voices were stored only for the clients that actually needed them.

flowchart TD A[Voice Catalogue] --> B[Global Tested Voices] A --> C[Client-specific Voices] B --> D[Available to All Clients] E[Client Dashboard] --> F[Enter Provider Voice ID] F --> G[Validate Voice] G --> H[Fetch Sample + Language] H --> I[Client Reviews Voice] I --> C C --> J[Available Only to That Client]

This also enabled the workflow to move toward self-service: a client could provide a voice ID, have it validated, preview the associated voice and language, and add it to their own configuration without requiring the same manual engineering path for every addition.

03

Fallback STT

Speech-to-text failures were particularly expensive in a live call. For some Indian-language conversations, the selected transcription provider could fail to produce a un-usable transcription. That failure could interrupt the voice stream and terminate the call.

I worked with a senior engineer on a fallback STT provider setting. When the primary transcription configuration failed, the system could fall back to a different STT configuration instead of allowing the transcription failure to end the conversation.

flowchart TD A[User Speech] --> B[Primary STT] B -->|Success| C[Continue Conversation] B -->|Transcription Failure| D[Fallback STT] D -->|Success| C D -->|Failure| E[Existing Failure Handling]

The fallback was initially enabled with a default configuration and, after testing, was made configurable as part of the broader voice settings system.

~95% fewer call-cut scenarios from this failure path
04

Reducing knowledge-base response latency

Nugget could answer using a client's knowledge base when the uploaded documentation contained a better answer than the normal workflow. The problem was latency: knowledge-base retrieval could sometimes take roughly three seconds.

In a voice conversation, that delay is very visible. I contributed to the design discussion and implementation of moving the knowledge-base work to a parallel path. Once transcription completed, the workflow and knowledge-base path could begin in parallel, followed by a classifier deciding which response to use.

flowchart TD A[User Transcription Complete] --> B[Workflow] A --> C[Knowledge Base] B --> D[Response Selection / Classifier] C --> D D --> E[Selected Response] E --> F[Voice Response]
~3s previous slow path
~1s after parallelization
05

QC Ticket Dashboard

I also built the backend for a new Quality Check ticket dashboard. QC tickets represented AI-based evaluations of conversations against parameters configured by clients viz for example confidence or adherence to defined guidelines.

Because the dashboard needed configurable views across many clients, I used a backend-driven approach for columns and filters rather than hard-coding each variation into multiple layers of the product.

I also reused the existing ticket dashboard's model and business logic where the behaviour overlapped, instead of creating a second independent implementation for the same concepts.

  • Backend-driven columns and filter configuration
  • Reusable filter / column interfaces
  • Reuse of existing ticket model and shared logic
  • OpenSearch-backed ticket querying
  • Production rollout across roughly 200 clients
06

A silent async failure

While working on QC tickets, I found a failure path around the channel where a generated ticket was supposed to be created.

Ticket creation happened asynchronously. If a new client's expected channel had not been created correctly, the downstream ticket creation could fail without surfacing a useful error to the original request. From the user's perspective, the ticket simply never appeared.

flowchart TD A[QC Evaluation Complete] --> B[Async Ticket Creation] B --> C{Channel Exists?} C -->|Yes| D[Create Ticket] C -->|No| E[Check / Create Default Channel] E --> D

I added a fallback path that checked for the expected channel and created the default channel when it was missing before proceeding with ticket creation.

The important lesson was not the fallback itself: asynchronous workflows need explicit failure visibility because there may be no synchronous caller waiting to expose the failure.

07

Production stack & systems

The work sat inside a much larger production platform, so a large part of the job was understanding and changing existing systems safely rather than building isolated services from scratch.

Systems and tooling I worked with across this work included:

  • OpenSearch for search and filtering workloads
  • Amazon SQS for asynchronous workflows
  • Datadog, Grafana, and AWS monitoring / observability
  • Provider integrations across STT and TTS systems
  • Interface-driven and factory-pattern abstractions in existing backend systems
  • Production debugging across asynchronous workflows
08

Impact

~95% reduction in targeted STT call-cut scenarios
~3s → ~1s KB response path in observed slow cases
~200 clients in QC dashboard rollout

The biggest shift for me was working inside a mature production system where a seemingly small configuration change could affect live customer calls.

Walkthrough

The original hackathon demo — from the integration problem and product idea to documentation discovery, RAG-assisted research, and the final workflow.

Original ZluBO hackathon demo 10 min walkthrough
01

Context

Zluri integrates with a large number of SaaS products so companies can manage onboarding, offboarding, access, and application workflows from one platform.

During my internship I worked across integrations myself, which gave me direct visibility into how much repetitive research happened before an integration could even be built.

02

The integration bottleneck

Every SaaS provider had different APIs, authentication models. Even before an integration could be implemented, an Integration Manager often had to manually read documentation and answer a recurring set of questions:

  • Does the provider expose the APIs Zluri needs?
  • Which endpoints support the required actions?
  • What authentication mechanism is required?
  • Are onboarding and offboarding actions supported?
  • Are there limitations or commercial constraints?
03

The idea

During Zluri's GenAI hackathon, I proposed changing the model rather than only making the existing Integration Manager workflow faster.

If a customer was already paying Zluri whenever they needed new integrations, why should every integration begin with a human at Zluri manually researching documentation? My idea was to turn that knowledge into a self-serve capability: let the customer specify the application they wanted to integrate and have the system discover the documentation, understand the APIs, and guide the integration process.

That created a bigger product opportunity: move from a service-heavy, integration-by-integration workflow toward a scalable subscription product where customers could continuously explore and enable integrations themselves, with Integration Managers stepping in only when automation could not resolve the case.

flowchart TD A[Customer Needs New Integration] --> B[Traditional Model] A --> C[ZluBO Model] B --> D[Integration Manager Research] D --> E[Manual Documentation Review] E --> F[Integration Delivered] C --> G[Customer Enters SaaS Provider] G --> H[Automated Documentation + API Research] H --> I{Enough Information?} I -->|Yes| J[Self-serve Integration Guidance] I -->|No| K[Integration Manager] J --> L[Recurring Self-serve Product] K --> L

The goal was therefore not only automation. It was to reduce the marginal human effort required for each new integration and make the integration capability itself more scalable as a product.

04

Documentation crawler

The first problem was collecting the documentation itself.

I built a Selenium-based crawler that could start from a provider's documentation and recursively traverse related pages while tracking visited URLs with a set to avoid repeatedly processing the same page.

flowchart TD A[SaaS / Provider Name] --> B[Find Documentation] B --> C[Selenium Crawler] C --> D[Extract Page Content] D --> E{New Relevant Links?} E -->|Yes| F[Add Unvisited URLs] F --> C E -->|No| G[Documentation Corpus]

The extracted documentation then became the source material for the retrieval and question-answering layer.

05

RAG workflow

The collected documentation was processed into a searchable knowledge base using LangChain and OpenAI-based retrieval / generation.

The system could then answer the repeated integration questions against the provider's own documentation rather than requiring an Integration Manager to manually search through dozens of pages.

flowchart TD A[Documentation Corpus] --> B[Process / Index Documents] B --> C[RAG Knowledge Base] D[Integration Question] --> E[Retrieve Relevant Context] C --> E E --> F[LLM] F --> G[Answer + Relevant Documentation Context]

This also meant that when automation could not confidently determine an answer, the same indexed documentation could still help the human reviewer investigate faster.

06

Human-in-the-loop workflow

I deliberately kept a manual fallback because provider documentation is inconsistent and some integration decisions require judgement.

flowchart TD A[New Integration Request] --> B[Discover + Crawl Documentation] B --> C[RAG / Capability Checks] C --> D{Enough Information?} D -->|Yes| E[Integration Requirements Identified] D -->|No| F[Integration Manager Review] F --> G[RAG-assisted Documentation Search] G --> E

The result was an assisted workflow where the automated path handled most of the repetitive discovery work and the Integration Manager concentrated on the smaller set of cases that still required manual validation.

07

Architecture

flowchart TD A[User / Integration Manager] --> B[Web Interface] B --> C[Provider / App Input] C --> D[Documentation Discovery] D --> E[Selenium Crawler] E --> F[Recursive Content Extraction] F --> G[Document Store / Knowledge Base] G --> H[LangChain Retrieval] H --> I[OpenAI / LLM] I --> J[Capability + API Answers] J --> K{Resolved?} K -->|Yes| L[Integration Research Complete] K -->|No| M[Human Review] M --> L
08

Results

~80% reduction in manual integration research
₹1.5L hackathon prize
1st Zluri GenAI Hackathon

ZluBO won first place in Zluri's GenAI hackathon and received a ₹1.5 lakh cash prize.

The project was presented internally, received positive feedback from company leadership, and contributed to me receiving a full-time offer after the internship.

09

Other work at Zluri

ZluBO came directly from the integration work I was already doing during the internship.

I worked across more than 100 SaaS integrations and integration migrations, dealing with provider APIs, testing, frontend and backend integration logic, and the practical differences between products such as Google Workspace, Zoom, HevoData, GitHub, and others.

That hands-on exposure to the workflow is what made the repetitive research bottleneck obvious enough to become the hackathon project.
